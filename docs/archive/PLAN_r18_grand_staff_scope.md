# Round 18 계획: 대보표 스코프 확장 — 5마디+ 긴 시스템 / 같은-clef 대보표

**상태**: 계획 수립 완료(2026-08-10), pod 미기동. 실행 전 검토용.

## 문제

1. **긴 시스템(5마디+) 조기 종료**: `sonatine_13p_35` 실사 촬영(7마디, 단일 시스템)을 로컬
   CPU로 r15_cropfix_coordconv에 직접 넣어 검증. 1~4마디는 정답과 토큰 단위로 완전히
   일치하는데, 4마디째에서 `barline-final`을 뱉고 조기 종료 — 5~7마디는 아예 생성 안 됨.
   같은 세션에서 실사 5장을 더 테스트했는데 전부 정확히 4마디에서 종료(그 중 4장은 정답도
   4마디라 일치, sonatine_13p_35만 정답 7마디라 불일치가 드러남). `project.md`에 이미
   문서화된 "입력 범위: 이미지 한 장 기준 최대 1~4마디" 학습 스코프와 정확히 일치하는
   증상 — 모델이 4마디를 넘는 걸 학습한 적이 없어서 못 하는 것.

2. **같은-clef 대보표 오인식**: 대보표 양쪽이 둘 다 낮은음자리표(또는 둘 다 높은음자리표)인
   경우, 모델이 위=치/아래=베이스라는 학습 편향을 실제 clef 기호보다 우선시해서 완전히
   잘못 인식함(clef뿐 아니라 음높이까지 틀림). music21+로컬 MuseScore로 "둘 다 베이스"
   합성 이미지를 만들어 직접 검증 완료 — 위쪽이 실제로는 C3~F3(베이스 음역)인데 모델은
   `clef-G`로 읽고 A4~D5(치 음역)로 예측. "둘 다 치"도 반대 방향으로 동일하게 오인식.

## 원인

- **긴 시스템**: `generate_scores.py`에 `MIN_MEASURES=2`/`MAX_MEASURES=6` 범위가 이미
  존재하지만(2026-07-31, 페이지 폭 동적 조정 `_make_dynamic_wide_page_style`도 이미 있음),
  r15 학습 시 실제로 쓰인 실사 메인 풀(`r12_all120_realphotos`, 120곡/1638장)과 replay 풀
  (`r12_replay_merged`, 8486장)의 마디 수 분포가 1~4마디 위주였던 것으로 보임 — 5마디+
  예시가 학습 데이터에 사실상 없었음.
- **같은-clef**: `mscz_to_tokens.py`(인코더)는 2026-08-03부터 이미 각 파트의 실제 clef를
  읽어서 `clef-G`/`clef-F` 토큰을 정확히 찍고 있음(newage19 held-out 실측에서 "베이스보표가
  치클렙으로 표기된 실제 사례" 발견 이후 수정됨). 하지만:
  - `token_to_notes.py`(디코더)는 그 토큰을 무시하고 "staff-bass 앞=treble/뒤=bass"로
    위치 기반 고정 — **이건 2026-08-10에 이미 수정 완료**(0단계, 커밋 `57effe3`,
    `tokens_to_score()`가 이제 `'clefs': [...]` 필드로 실제 clef를 반환하고
    `server.py`/`handler.py`도 이 값을 씀).
  - 하지만 **모델 자체가 "위=치/아래=베이스" 학습 데이터로만 훈련됨** — `generate_scores.py`가
    대보표 생성 시 `treble_part`는 항상 `clef.TrebleClef()`, `bass_part`는 항상
    `clef.BassClef()`로 하드코딩(`CLEF_CHANGE_PROB`로 마디 중간 일시 전환만 지원, 시스템
    전체가 같은 clef인 경우는 생성 자체가 안 됨). 디코더를 고쳐도 모델이 애초에 그런
    입력을 본 적이 없어 여전히 오인식 — 검증으로 확인됨(위 "문제" 2번).

## 남은 작업 (pod 재개 시)

### A. 데이터 생성 코드 변경 (아직 미구현)

**데이터 소스 방침(2026-08-10 사용자 확정)**: 이번 라운드는 **100% 깨끗한 합성 데이터만**
쓴다 — 실사 촬영은 이번 신규 축(같은-clef/긴 시스템)에 추가하지 않는다. r16/r17 때
replay에 실사 이미지가 섞여 들어간 적이 있었는데 그때 결과가 r15보다 낮았다는 게 확인된
전례라, 이번엔 그 실수를 반복하지 않는다. `r12_all120_realphotos`(실사 메인 풀)는 기존
그대로 손대지 않고 유지, **새로 만드는 데이터는 전부 합성**:
1. 높은음자리표 + 높은음자리표 (둘 다 치)
2. 낮은음자리표 + 낮은음자리표 (둘 다 베이스)
3. 한 시스템 안에 여러 마디(5마디+) — 기존 대보표(위=치/아래=베이스) 형태에도 적용

`train/generate_scores.py`:
1. **마디 수 확장**: 대보표 생성 시 마디 수 샘플링 범위를 넓힘(예: `MAX_MEASURES`를
   6→8로, 실측 sonatine_13p_35가 7마디였던 걸 여유 있게 커버). 기존 인프라
   (`_make_dynamic_wide_page_style`) 재사용 — 8마디에서도 한 시스템 안에 줄바꿈 없이
   들어가는지 로컬에서 먼저 렌더 확인 필요(POD_TRAINING_CHECKLIST.md 3번 항목 — 렌더
   직후 실제 픽셀 크기/줄바꿈 여부를 눈으로 확인할 것, 스크립트가 맞다고 가정하지 말 것).
2. **같은-clef 대보표 모드 신규 추가**: `SAME_CLEF_PROB`(가칭) 전역 추가, 트리거되면
   `treble_part`/`bass_part` 둘 다 같은 `clef.TrebleClef()` 또는 `clef.BassClef()`로 생성.
   음역대(pitch pool)는 두 파트가 같은 clef라도 시각적으로 구분되게 약간 겹치지 않는
   범위로 분리(예: 둘 다 베이스면 위쪽은 C3~C4, 아래쪽은 E1~G2 등 — 정확한 분리 기준은
   실사 사례를 더 확보해서 참고하는 게 이상적이나, 없으면 임의로 정해도 됨).
   `mscz_to_tokens.py`는 이미 실제 clef를 읽으므로 이 쪽은 수정 불필요.
3. 위 1·2번은 서로 독립된 축이라 조합 가능 — 예를 들어 "둘 다 베이스 + 7마디" 같은
   샘플도 자연스럽게 나올 수 있게, 마디 수 샘플링과 같은-clef 트리거를 같은 호출
   안에서 각각 독립 확률로 굴리면 됨.

### C. "한 번에 축 하나만" 원칙 검토 필요 — 사용자 결정 요청

이 프로젝트는 r16/r17처럼 **한 라운드에 변수 하나만 격리해서 학습**해온 전례가 있음(결과
원인 분석이 깨끗해짐). 이번엔 축이 2개(긴 시스템 / 같은-clef) — 마감(8/17)이 임박해서
방법을 골라야 함:

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 한 라운드에 둘 다 섞어서** | 학습 1회로 끝, 시간 절약 | 결과가 나빠지면 둘 중 뭐가 원인인지 분리 안 됨(r16/r17 전례상 흔함) |
| **B. 2라운드로 분리**(r18=같은-clef, r19=긴 시스템, 둘 다 r15에서 독립 분기 후 성공하면 결합) | 원인 귀속이 깨끗함, 기존 방법론과 일치 | 학습을 2번 돌려야 함(시간 2배) |

  `diag_new6_errors.py`류로 신규 실사곡 재검증 + **이번 변경의 직접 타깃 지표**로
  (1) 5마디+ 실사(sonatine_13p_35 등)에서 마디 5~7이 실제로 생성되는지,
  (2) 같은-clef 합성 테스트(이번 세션에서 만든 것과 동일 방식)로 clef 오인식이 줄었는지
  직접 재확인할 것.

## 실행 결과 (2026-08-10, r18 → r18b)

**진행한 것**: A(데이터 생성 코드: `SAME_CLEF_PROB`/`--same-clef-mode`, 측정 범위 확장)를 구현,
pod에서 3000장 생성(both_treble/both_bass/장문 각 1000, ottava/tie 제외) → `r18_replay_merged`
(8486+3000=11486장) → r15에서 resume 학습(`r18_grand_staff_scope`, 15에폭, best TF acc 90.0%).

**중간 발견**: held-out 합성 30장 재검증 중 상당수(12/30)가 예측 토큰 0개로 실패 — 원인 추적
결과 모델이 아니라 `preprocess()`의 `TARGET_W=1920` 고정폭 리사이즈가 8마디급 와이드 이미지의
세로 해상도를 과도하게 눌러(196x1920까지 붕괴) 오선 검출 자체가 실패하는 버그였음(`dataset.py`
수정, 커밋 `1d2ded5`). 학습 로그에 "12626 samples (1453 skipped)"로 남아있던 스킵 표본 중
상당수가 이 버그로 학습에서 아예 빠졌던 것으로 확인 → 캐시 삭제 후 **r18에서 이어서 재학습**
(`r18b_grand_staff_refit`, 15에폭, best TF acc 93.27%, 스킵 1453→392로 감소, 13696 samples 로드).

**최종 검증 — r15와의 공정 비교(중요)**: r15의 공식 87.2% 근거였던 실사 12곡 중 같은-clef인
`sonatine_23_42` 1곡만 제외한 11곡(32장, 정상 클렙+1~4마디 — r15가 원래 잘하던 스코프)으로
r15 vs r18b 직접 비교:

| | r15(프로덕션) | r18b |
|---|---|---|
| 11곡 전체 평균 | **90.3%** | **85.2%**(-5.1%p) |

11곡 중 6곡 하락(3곡은 두 자릿수: sonatine_22_30 -26.4%p, sonatine_23_38 -14.6%p,
newage21 -10.9%p), 4곡 개선, 1곡 동일 — **순 하락**. 같은-clef/장문 축 자체는 크게 개선됐음
(held-out 합성 기준 오선 검출 성공 샘플만 놓고 보면 48.4%→83.5%)이지만, r15가 원래 잘하던
정상 스코프에서 이 정도로 후퇴하는 건 r16/r17 기각 때와 같은 패턴.

**결론(2026-08-10 확정)**: r16/r17에 이어 **r18b도 동일한 이유로 프로덕션 채택 보류** —
r15를 계속 프로덕션 체크포인트로 유지. r18b는 배포하지 않고 pod storage에만 보관(로컬
`train/checkpoints/`에도 안 내려받음). **이번 라운드의 학습 자체는 여기서 중단**(사용자 확정,
2026-08-10) — 재시도는 추후 별도 세션에서.

**패턴에 대한 평가**: "replay 비중이 큰 재학습을 할수록 체크포인트 성능이 저하된다"는
가설은 이번까지 **독립적으로 3번(r16, r17, r18b) 재현**돼서 우연이 아닌 실제 경향으로 볼
근거가 충분함. 다만 "반복할수록(r18→r18b처럼 두 번째 이어학습이 첫 번째보다 더 나쁘다)"까지는
증거가 없음 — r18(1차, 버그 수정 전) 자체를 이 11곡 실사셋으로 측정한 적이 없어서 r18 vs
r18b의 직접 비교는 못 함. 원인은 TRAINING_REPORT.md의 r16/r17 항목에서도 이미
"LR 재가열/과적합/새 축 자체의 부작용인지 등 미결"로 남아있던 것과 같은 미해결 질문.

**다음에 시도해볼 만한 것(신규 실사 없이 가능한 것부터)**:
1. replay_count를 전체(11486) 대신 real 메인 풀(1638) 대비 낮은 비율로 줄여서 재시도(현재
   비율 약 7:1로 replay가 압도적 — real 신호가 희석됐을 가능성).
2. 학습률/에폭 수 축소, 또는 encoder freeze 구간을 더 길게(현재 freeze_epochs=0).
3. 그래도 안 되면 신규 실사 이미지 확보(더 근본적이지만 시간이 오래 걸림 — 마감 임박 고려 시
   후순위 추천).
