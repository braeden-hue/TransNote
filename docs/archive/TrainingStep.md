# TrainingStep.md — OMR 인식 개선 학습 단계 로드맵

마지막 업데이트: 2026-07-30

이 문서는 round3train 파이프라인의 다음 학습 단계들을 순서대로 정리한 로드맵이다.
세부 학습 로그/체크포인트 계보는 `PODPLAN.md`에, 실제 실행용 스크립트는 `round3train/curriculum_*.sh`에 있다.
여기서는 "왜 이 순서인지", "각 단계가 무엇을 고치는지"만 간결하게 정리한다.

## 현재 상태 (2026-07-28 기준)

- **로컬에 남아있는 최신 체크포인트**: `secrets/checkpoints/seq2seq_noise2_best.pt` (최신),
  `seq2seq_chopin_style_best.pt` (한 단계 전). 계보: `...→ p2s5n5 → chopin_style → noise2`.
- 포드(RunPod)는 이번 라운드 대부분 꺼져있었음 — 아래 단계들은 로컬 설계까지만 끝난 상태이고,
  각 커리큘럼 스크립트 상단에 "포드 재접속 후 확인" 사전조건이 명시돼 있다.
- 로컬 스트레스 테스트로 두 가지 구체적 약점을 발견했고, 이게 아래 Step 1/2의 근거다.

## 2026-07-30 긴급 수정 — 대보표 다중 시스템 사고 (모든 스텝 대보표 생성에 적용됨)

**배경**: 스텝별 데이터를 로컬(노트북)에서 직접 만들어보다가 사용자가 발견 — "png 기준으로
학습할 때 무조건 오선 한 줄이어야 함". 확인해보니 실제 카메라 캡처(`lib/screens/
guided_camera_screen.dart`)가 "오선 1개"/"대보표(2개)" 두 모드 모두 **항상 시스템 1개만**
프레임에 담도록 설계돼 있음(코드 주석: "자동 검출의 모호함을 촬영 UX로 원천 차단하는 접근").
그런데 대보표 생성(`build_score_r3`)은 이 전제를 어기고 있었음 — 두 가지 문제를 실측으로 확인:

1. **`--density-break`가 다중 시스템을 만듦**: 기존 6register/7density 커리큘럼 스크립트가
   대보표 생성에 이 플래그를 쓰고 있었는데, 실측 194장 중 149장(77%)이 시스템 2개 이상.
   `dataset.py`가 시스템별로 크롭해서 학습 샘플을 만들긴 하지만(그래서 라벨 자체는 안
   깨짐), 실제 카메라가 절대 만들지 않는 형태의 원본 이미지로 학습하는 셈이라 제거.
2. **`--density-break` 없이도 조용히 2페이지로 밀려남(더 심각)**: 대보표는 단일 오선과 달리
   페이지 폭/높이를 넓히는 처리가 없어서, 내용이 조금만 조밀해지면(Step 2의
   `--short-note-bias 2.0` 등) MuseScore가 기본 페이지 높이 기준으로 시스템을 통째로
   2페이지로 밀어버림. 이때 `system_breaks`는 여전히 `[]`로 기록되고, 우리가 캡처하는
   1페이지는 **완전히 빈 이미지**가 되는데 코드가 이를 "성공"으로 잘못 판정 — 실측으로
   재현(4마디 중 4번째 마디가 통째로 밀려나 1페이지가 흰 화면).

**대응**:
- 모든 커리큘럼 스크립트(`curriculum_6register.sh`/`curriculum_6b_tie.sh`/
  `curriculum_7density.sh`)의 대보표 생성 호출에서 `--density-break` 제거.
- `generate_scores.py`: 대보표도 단일 오선처럼 항상 넓은 페이지 스타일 적용(`wide_page=True`
  무조건, 기존엔 `args.single_staff`일 때만). 다만 단일 오선용 `wide_page.mss`(높이 4in, 치+
  베이스 두 줄엔 부족)를 그대로 쓰면 오히려 2페이지 사고가 나서, 대보표 전용
  `wide_page_grand.mss`(높이 8in)를 새로 만들어 `render_png(..., grand=True)`일 때 사용.
  **처음 이 fix를 넣을 때 실제 호출부(`render_png(musescore_path, ...)`)에 `grand=` 인자
  넘기는 걸 빼먹어서 15/15가 전부 빈 이미지로 나온 걸 한 번 잡았음** — 그래서 저장 직전
  `_looks_blank()`(PIL로 거의 순백인지 확인)를 추가해 이런 사고가 다시 나도 조용히
  라벨에 섞여 들어가지 않고 스킵되도록 방어선을 이중으로 둠.
- 검증: 문제 재현했던 정확히 같은 조건(seed=55, 4마디, short-note-bias 2.0)으로 재생성해서
  15/15 정상(빈 이미지 0건) 확인. Step 1의 실제 파라미터(1~4마디, cross-register-prob 0.35,
  density-break 없음)로도 40/40 정상(system_breaks 전부 [], 빈 이미지 0건) 재확인 완료.
- **한 번 더 사고**: 처음 fix를 넣을 때 `render_png()` 함수 정의엔 `grand=` 인자를 추가해놓고
  실제 호출부(`render_png(musescore_path, ...)`)에 넘기는 걸 빼먹어서, 재현 테스트에서
  15/15 전부 빈 이미지로 나온 걸 `_looks_blank()` 방어선이 잡아냄 — 방어선이 없었다면
  조용히 통과했을 사고. 호출부 수정 후 재검증(15/15 정상)까지 완료.

## 2026-07-30 수정 — 교차음역 상/하한 clamp (Step 1)

**배경**: 사용자가 `round3train/data/local_pools/range.mscz`(직접 만든 참고 파일)로 원하는
음역 상/하한을 지정 — 높은음자리표 최저~최고 = **C3~B6**, 낮은음자리표 최저~최고 = **E1~B4**
(mscz를 MuseScore로 musicxml 변환 후 music21로 실측). 기존 `CROSS_REGISTER_PROB` 로직은 swap
모드에서 치보표에 `BASS_PITCHES`(바닥 C2)를, 베이스보표에 `TREBLE_PITCHES`(천장 B5)를 그대로
바꿔치기해서, 치가 C2까지 내려가거나(하한 C3 위반) 베이스가 B5까지 올라가는(상한 B4 위반)
경우가 있었음.

**대응**: `TREBLE_LOW_PITCHES`(C3~B3)/`BASS_HIGH_PITCHES`(C4~B4) 전용 풀을 새로 만들어
swap/both_high/both_low 모드가 이 범위 안에서만 극단 음역을 만들도록 clamp. 정상 풀
(`TREBLE_PITCHES` C4~B5, `BASS_PITCHES` C2~B3)은 이미 range.mscz 범위 안이라 그대로 둠.
검증: cross-register 300개 샘플 실측 결과 위반 0건.

## 2026-07-30 추가 — 선호 음역 구간(70%) + 크레센도/옥타브 완전 제거 (Step 1)

**배경**: range.mscz 상/하한 확인 뒤, 사용자가 같은 파일에 음 4개씩(치: D3/A3/A5/A6, 베이스:
G1/C2/F4/B4)을 더 찍어서 "각 클렙당 두 개의 분리된 선호 구간(저음역+고음역)"을 지정 — 즉
치보표는 **D3~A3 또는 A5~A6**, 베이스는 **G1~C2 또는 F4~B4**(둘 다 각자 오선에서 멀리 떨어져
덧줄이 많이 필요한 구간) 안에서 음이 **70% 확률로** 나오길 원함. 추가로 크레센도/디크레센도
(hairpin)·옥타브(ottava) 기호는 완전히 안 나오게 요청.

**vocab 충돌 발견**: 베이스 저음 구간 G1은 `tokenizer258.json` vocab 최저(C2) 밖 — 그대로
생성하면 `<UNK>`로 깨질 위험. 사용자 확인 후 **C2~E2로 대체**(vocab 최저부터 시작, 여전히
베이스 오선 아래 여러 덧줄 필요한 구간이라 취지 유지).

**대응**:
- `TREBLE_PREFERRED_PITCHES`(D3~A3 ∪ A5~A6) / `BASS_PREFERRED_PITCHES`(C2~E2 ∪ F4~B4) 추가.
  `_pitch_pool()`이 옥타브 2~6만 스캔하던 걸 1~6으로 확장(G1 계열 확인용, 기존 호출엔 영향 없음).
- `_pick_pitch()`에 `preferred_pool` 인자 추가 — `PREFERRED_REGISTER_PROB`(신규
  `--preferred-register-prob`) 확률로 먼저 후보를 `pool ∩ preferred_pool`로 좁힌 뒤(교집합
  비면 원래 pool 유지) 기존 MELODIC_BIAS/DIATONIC_BIAS를 그 위에 적용. `_build_part()`가
  이 인자를 받아 `build_score_r3`/`build_score_single_staff` 양쪽에서 클렙에 맞는 선호
  풀을 넘김 — cross-register로 이미 극단 풀(TREBLE_LOW_PITCHES 등)을 쓰는 경우에도 교집합
  방식이라 안전하게 동작.
- `--hairpin-prob 0 --ottava-prob 0`을 각 커리큘럼 스크립트의 COMMON_ARGS(공통 인자)로
  이동 — 예전엔 대보표 생성 호출에만 붙어있어서 단일오선 쪽에 크레센도가 새고 있었음
  (사용자 지적으로 발견).
- 검증(로컬 200개 대보표 샘플, PREFERRED_REGISTER_PROB=0.7): vocab 밖 토큰 0건, hairpin/ottava
  토큰 0건, 치 선호구간 비율 69.8%, 베이스 선호구간 비율 71.1%(목표 70%에 부합). 단일오선도
  hairpin 0건 확인. PREFERRED_REGISTER_PROB=0(기본)일 때 회귀 없음(크래시 없음) 확인.
  Step 1 실제 명령줄(1~4마디, cross-register-prob 0.35, preferred-register-prob 0.7,
  hairpin/ottava 0)로 10/10 생성 성공까지 end-to-end 확인.
- `curriculum_6register.sh`/`local_generate_all.sh`의 Step 1 COMMON_ARGS에
  `--preferred-register-prob 0.7` 추가(range.mscz가 Step 1 전용 참고 파일이라 Step 1에만
  적용, tie1/7den1은 미적용).

## 2026-07-30 추가 — 대원칙(음정 간격 상한) + 붙임줄 마디내/화음 지원

사용자가 지정한 4가지 "대원칙":
1. 두 음표(직전 음 기준) 간 계이름 간격은 **8도(옥타브) 이하** — 항상 적용, 옵션 아님.
2. 화음은 최대 3음까지 — 이미 `CHORD_MAX_NOTES=3`이 기본값이라 별도 조치 불필요(확인만).
3. 붙임줄이 **마디 안에서 끝나는 경우 / 마디를 넘어가는 경우 둘 다** 지원.
4. 붙임줄은 **최대 2음 화음끼리도** 가능하지만, 단음-단음 붙임줄보다 현저히 낮은 확률로.

**간격 단위 해석(사용자 확인 필요 시 조정)**: "8도"는 옥타브 자체를 가리키는 명칭이라 반음
12개로 고정(모호함 없음). "7도"(촘촘한 연속 그룹 전용, 아래 참고)는 단7도(10반음)/장7도
(11반음)로 갈릴 수 있어 완전히 명확하진 않으나 "옥타브 바로 아래까지"로 해석해 11로 잡음.

**대응**:
- `MAX_MELODIC_INTERVAL=12`(8도), `MAX_DENSE_MELODIC_INTERVAL=11`(7도) 추가. `_pick_pitch()`에
  `max_interval` 인자 추가 — 확률이 아니라 **항상 적용되는 하드 캡**(preferred_pool/
  MELODIC_BIAS보다 먼저, 가장 우선순위 높게 적용). 직전 음도 이번 음도 8분음표 이하(ql≤0.5)면
  "촘촘한 연속 그룹"으로 보고 7도 캡, 아니면 8도 캡 — 사용자가 명시한 "2개/4개 묶음" 판정을
  "직전+이번 음 둘 다 짧다"로 근사(정확한 비트 그룹핑 대신 실용적 근사).
  - 단음 선택, 화음 루트 선택, 3연음(3개 다 촘촘한 그룹으로 취급, 7도 캡) 세 곳 모두 적용.
  - **버그 하나 발견+수정**: 화음의 "추가 음"(root 이외)이 `CHORD_MAX_INTERVAL`(기존, 화음
    내부 음정 상한)만 적용받고 이 새 간격 캡은 안 받고 있어서, root는 정상인데 정렬 후
    `chosen[0]`(화음의 대표 피치이자 다음 음의 기준점)이 캡을 넘는 사례를 로컬 실측으로
    발견(예: 직전 음 B-3, 화음이 [A2,E3,F3]으로 나와 13반음 차이). extra 후보 필터에도
    같은 간격 캡을 추가해서 해결 — 6781쌍(단일오선)·5824쌍(대보표+교차음역) 재검증 위반 0건.
- 붙임줄 로직 전면 재설계: 기존엔 "마디 끝에서만 시작" 가능했음. 이제 마디 시작 시점에
  `measure_tie_pending = TIE_PROB 확률로 결정`, 그 마디를 생성하는 도중 **처음 마주치는
  이어붙이기 후보**(단음 또는 2음 화음)에서 실제로 시작 — 그게 마디 마지막 음표면 자연히
  다음 마디로 넘어가는 tie, 아니면 마디 안에서 끝나는 tie(동일 메커니즘, 별도 분기 불필요).
  3음 화음은 애초에 후보에서 제외. 2음 화음이 후보로 걸리면 `CHORD_TIE_SUBPROB=0.15`
  확률로만 실제 시작(그 외엔 다음 기회를 기다림) — 화음-화음 tie를 단음-단음보다
  현저히 드물게 함. 마지막 마디의 마지막 슬롯(이어붙일 자리가 아예 없음)에서는 시작 안 함.
  - 검증(단일오선 400개, TIE_PROB=1.0): tie 1533건(마디안 1434 / 마디넘음 99, 둘 다 발생),
    화음tie 10건(0.7%, "현저히 낮음" 충족), 피치 불일치 0건.
- 회귀: 새 플래그 전부 기본값(0)일 때 크래시 없음, 기존 TIE_PROB=0 회귀(tie 토큰 0건)도 유지.

## Step 1 (우선순위 최상) — 교차 음역(옥타브) 복구

**스크립트**: `round3train/curriculum_6register.sh` (resume: `noise2`)

**발견한 문제**: 대보표 두 오선이 둘 다 같은 음역(둘 다 높음/둘 다 낮음)이거나 서로 뒤바뀐 경우
(치가 낮은 음역, 베이스가 높은 음역 — 즉 덧줄이 많이 붙는 케이스)를 테스트했더니 완전일치 0/10.
클렙(음자리표) 판독 자체는 정상이었지만(예측 토큰의 clef-G/clef-F는 GT와 일치), **실제 음높이
(덧줄 개수)를 무시하고 그 음자리표의 "전형적 음역"으로 회귀**하는 뚜렷한 편향을 확인함
(예: 베이스 오선에 실제로 높은 음이 있어도 예측은 B3~C2 근처로, 치 오선에 실제로 낮은 음이
있어도 예측은 C4~D4 근처로 되돌아감). 리듬(duration)은 대부분 맞았음 — 문제가 정확히
"클렙 기준 덧줄을 세어 정확한 음이름을 계산하는" 부분에 국한됨.

**대응**: `generate_scores.py`에 `CROSS_REGISTER_PROB`/`--cross-register-prob` 추가. 이 확률로
대보표 치/베이스 피치 풀을 `swap`(치↔베이스 음역 교환) / `both_high`(둘 다 치음역) /
`both_low`(둘 다 베이스음역) 중 하나로 바꿔서 덧줄 많은 케이스를 생성. 클렙 표기 자체는 항상
정상(치 위/베이스 아래) 유지 — 바뀌는 건 그 안의 실제 피치뿐.

**이 단계가 Step 2보다 먼저인 이유**: 리듬 밀도보다 더 근본적인 편향(음높이 인식 자체가
클렙 사전확률에 의존)이라 판단해서 우선순위를 앞에 둠.

## Step 1.5 — 붙임줄(tie) 복구

**스크립트**: `round3train/curriculum_6b_tie.sh` (resume: Step 1 산출물 `6reg1`,
`--resume_tokenizer tokenizer258_pre_tie.json` 필수 — 아래 참고)

**우선순위 배경(2026-07-30, 사용자 확인)**: 사용자가 이전 학습 실행에서 붙임줄이 있는 구간을
모델이 인식하지 못했고, 그 여파로 붙임줄 이후에 이어지는 음표 인식까지 **연쇄적으로 무너졌다**고
보고함. 오토리그레시브 디코더 특성상 한 지점의 오류가 그 뒤 컨텍스트 전체를 오염시켰을 가능성이
높음 — Step 1(교차음역)/Step 2(리듬밀도)와 같은 유형("학습 데이터에 없던 케이스 → 완전 붕괴")의
실전 관찰이라, 원래 계획("Step 1/2 완료 후 재평가")보다 앞당겨 Step 2(리듬 밀도)보다 먼저 두기로
함(사용자 확인 완료, 자세한 근거는 메모리 `project_tie_recognition_failure.md` 참고).

**발견한 문제**: 붙임줄은 클렙과 달리 vocab에 토큰 자체가 없었음(`tokenizer258.json` 258개 전부
확인, tie 관련 항목 전무). `mscz_to_tokens.py`도 music21 `Note.tie`를 아예 조회하지 않아서, 실사
정답 mscz(`ml/data/test/`, 예: 쇼팽 곡)에 진짜 붙임줄이 있어도 각 조각이 독립된 반복음처럼
라벨링되고 있었고, `generate_scores.py`도 마디를 넘는 음표를 아예 생성하지 않아 합성 데이터에도
tie 노출이 전무했음.

**대응(구현 완료, 2026-07-30)**:
- vocab을 1개 늘려서 해결 — `tokenizer258.json`에 `tie` 단일 플래그 토큰 추가(258→259, ID 258).
  슬러(`slur-start`/`slur-end`, 임의 개수 음표를 감싸는 구간 마커)와 달리 붙임줄은 항상 바로
  인접한 같은 피치 음표 쌍만 연결하므로, "이 음표가 바로 다음 같은 피치 음표로 이어진다"는 뜻의
  마커 하나면 충분 — 도착점(끝 음표)에는 아무 토큰도 안 붙임(체인 길이 항상 2).
- `mscz_to_tokens.py`의 `_emit_one()`이 `Note.tie`(start/continue)를 감지해 `tie` 토큰 emit —
  단위 테스트로 검증(`note-C4 dur-1/4 tie note-C4 dur-1/4` 형태 확인).
- `generate_scores.py`에 `TIE_PROB`/`--tie-prob` 추가(기본 0=끔, 기존 확률 플래그들과 동일 패턴).
  `_build_part()`가 마디 끝 "일반 단음"(쉼표/화음/3연음 제외)을 붙임줄 시작점으로 삼아 다음 마디
  첫 음표를 같은 피치로 강제하고 실제 music21 `Tie` 객체도 삽입 — single-staff/grand-staff 양쪽
  경로에 공유 적용됨. 마디 중간 클렙 전환(`--clef-change-prob`)과 같은 파트에서 동시 사용 시
  해당 파트는 tie가 자동으로 꺼짐(상호작용 미검증이라 안전하게 분리).
- `error_breakdown.py`에 `tie_context_mask()` 추가 — `dotted8_context_mask()`와 동일 패턴으로
  tie 토큰 자신 + 착지점 음표의 정확도만 따로 리포트("붙임줄(tie) 및 착지점 정확도"). 이게 바로
  사용자가 보고한 증상이 실제로 고쳐졌는지 보는 직접 지표.
- 검증 완료(로컬): `TIE_PROB=0`(기본)일 때 tie 토큰 0건(단일 오선 200개·대보표 50개 전부, 회귀
  없음), `=1.0`일 때 단일 오선 300개 샘플에서 tie 697건 전부 앞뒤 피치 일치, 대보표 40/40 등장,
  `score.write('musicxml')` 정상, 클렙전환+tie 동시 옵션도 크래시 없음. `inference.py`
  (`correct_time_signature`/`_measure_beat_sum`)는 미지 토큰을 0-duration으로 관대하게 처리하는
  구조라 코드 변경 불필요(직접 확인).
- **가중치 파일**: vocab이 258→259로 실제 늘어나므로 클렙 사례와 달리 완전 무영향은 아님 — 다만
  `round3train/train.py:247` `load_ckpt_partial_vocab()`이 토큰 **문자열** 기준으로 old/new vocab을
  매칭해 겹치는 258개 토큰의 학습된 가중치를 그대로 이어받고 새 `tie` 행만 랜덤 초기화하는 기존
  메커니즘(1,013→258 vocab 마이그레이션 때 이미 실전 사용)을 그대로 재사용 — `round3train/
  tokenizer258_pre_tie.json`(258개, tie 없음, git HEAD 스냅샷)을 `--resume_tokenizer`로 넘김. 이
  단계 이후(Step 2 등)는 vocab이 259개로 고정되므로 `--resume_tokenizer` 다시 불필요.
- 커리큘럼 스크립트 작성 완료(`curriculum_6b_tie.sh`), 포드 실행은 아직 미착수.

## Step 2 — 리듬 밀도 복구 (8분/16분음표 묶음 + 점8분+16분음표)

**스크립트**: `round3train/curriculum_7density.sh` (resume: Step 1.5 산출물 `tie1`, 순서 변경
2026-07-30 — 기존엔 Step 1 산출물 `6reg1`을 직접 resume했음)

**발견한 문제**: `generate_scores.py`의 기본 duration 가중치가 점8분음표(`dur-3/16`)에 0.5%밖에
배정돼 있지 않아서(1/16의 8%, 3/8의 1.5%보다도 낮음) "점8분+16분음표" 리듬 셀이 학습 데이터에
거의 등장하지 않음. 또한 마디당 음표가 조밀하게(8분/16분음표 연속 묶음 위주) 들어찬 입력 자체를
스트레스 테스트했더니 완전일치 0/24 — 박자 오인식(4/4를 3/4로), 존재하지 않는 화음 대량 환각 등
전면적인 붕괴를 확인함(자체 val_acc는 96~99%였는데도).

**대응**:
- `DOTTED8_BIAS`/`--dotted8-bias` 추가 — 점8분음표(dur-3/16) 가중치를 (1+값)배로 올림
  (10.0 → 약 5.2%, 1/16과 비슷한 수준).
- `SHORT_NOTE_BIAS`/`--short-note-bias` (기존 기능) 사용 — 1/8·1/16 가중치를 올려 8분/16분음표
  2개·4개 연속 묶음 빈도를 높임. 로컬 10장 테스트(local_dense_pool)로 8분음표 2·3·4개 연속,
  16분음표 2·3개 연속, 점8분+16분 조합 모두 등장 확인 완료.
- `error_breakdown.py`에 `dotted8_context_mask()` 추가 — 점8분음표+바로 다음 음의 계이름
  정확도만 따로 리포트(전체 val_acc에 묻히지 않도록).

## Step 2.5 (생성 로직 구현 완료, 실제 커리큘럼 실행은 미착수) — 마디 중간 클렙(음자리표) 전환

**배경**: 한 보표(치 또는 베이스) 내에서 마디 중간에 음자리표가 바뀌는 표준 표기(예: 치보표가
극저음 구간에서 마디 중간에 낮은음자리로 잠시 전환 후 복귀)를 기존 파이프라인이 다루지 않았음.
`clef-{G|F}` 토큰 자체는 vocab에 이미 있지만(`round3train/generate_scores.py`), 보표당 최초 1회만
발행되고 마디 중간 재발행 케이스가 데이터에 없었음.

**커스텀 악보 규칙/렌더링(연습용 앱)은 먼저 반영함(2026-07-29)** — 치=청보라(#6C63FF)/베이스=
호박색(#FFB347) 반투명 칸 배경으로 클렙 전환 구간을 구분 표시(`docs/music-notation-rule-designer.md`
참고). 이건 round3train ML 파이프라인과는 별개(Flutter/웹 연습 앱 데이터 모델).

**round3train 생성 로직도 구현 완료(2026-07-30)**:
- `generate_scores.py`에 `CLEF_CHANGE_PROB`/`--clef-change-prob` 추가 (기본 0=끔, 기존
  SHORT_NOTE_BIAS/DOTTED8_BIAS/CROSS_REGISTER_PROB와 동일 패턴). `--single-staff` 생성 시에만
  적용 — 대보표(`build_score_r3`)는 대상 아님(확정된 정의가 "한 보표 내부"이고, `staff-bass`
  인터리빙·`dataset.py`의 대보표 분할 로직과의 상호작용을 아직 검증하지 않아 범위를 좁힘).
- 구현 방식: `_build_part()`가 선택적 `clef_events` 리스트를 받아, 마디 내 임의 오프셋(quarterLength
  기준, 실제 음표 경계에 맞춰 삽입)에 반대쪽 클렙으로 전환 후 이후 마디에서 원래 클렙으로 되돌아오는
  두 이벤트를 처리. 실제 music21 `Clef` 객체가 그 오프셋에 삽입되므로 렌더링 이미지에도 반영되고,
  토큰 스트림에도 `clef-F`/`clef-G`가 시퀀스 중간에 재등장. **새 vocab 토큰 불필요** — 기존
  `clef-G`/`clef-F` 토큰 재사용이라 tokenizer.json 변경 없음.
- 검증 완료(로컬): `CLEF_CHANGE_PROB=0`(기본값)일 때 mid-stream clef 토큰 0/200 (회귀 없음),
  `=1.0`일 때 50/50 등장, 각 케이스 `score.write('musicxml')` 정상, 그랜드 스태프 경로
  (`build_score_r3`) 별도 스모크 테스트 정상.
- **가중치 파일 영향 없음**: vocab/토크나이저 크기·모델 아키텍처 변경이 전혀 없으므로(Step 1/2와
  동일한 패턴), 기존 체크포인트(`secrets/checkpoints/seq2seq_noise2_best.pt` 등)를 그대로
  `--resume`해서 이어 학습 가능. 다만 새 분포를 실제로 학습하려면 이 확률을 켠 데이터로 파인튜닝을
  돌려야 하며(생성만으로는 모델이 자동으로 학습하지 않음), 커리큘럼 스크립트(`curriculum_*.sh`)
  작성 및 포드 실행은 아직 미착수 — Step 1/2 완료 후 우선순위 재평가.

## Step 3 — 실사(직접 촬영) 이미지 학습

Step 1/2로 합성 도메인 정확도를 정상화한 뒤 진행. 실사 이미지의 역할은 **캡처 조건(조명/각도/
블러/화면 반사 등) 적응**으로 한정 — 음악적 내용(리듬/음높이) 다양성은 Step 1/2까지의 합성
데이터가 커버해야 함.

### 3-1. 정답 악보(mscz) 준비 — 완료
- `ml/data/test/<곡이름>/` 각 폴더에 손으로 만든 mscz 정답지 50개 준비 완료.
- `round3train/mscz_to_tokens.py`(신규): mscz → MuseScore CLI로 musicxml 변환 → music21 파싱 →
  tokenizer258.json 규격 토큰 JSON 생성. 폴더명과 일치하는 JSON이 이미 있으면 skip.
  - 3연음(triplet) 자동 감지 → `tuplet-3-start`/`dur-1/8`×3/`tuplet-3-end`로 정확히 인코딩.
  - 어휘에 없는 이명동음 철자(Fb/Cb/E#/B# 등)를 MIDI 기준으로 재계산해 올바른 철자+옥타브로 자동 정정.
  - `dynamic-fz` → `dynamic-f` 치환(어휘에 없는 다이나믹 표기 보정, 사용자 확인 완료).
  - 어휘 범위 밖 음(C2~B6 밖, 예: Bb1)은 임의로 바꾸지 않고 경고만 남김 — `chop18_183`,
    `chop18_189`에 알려진 한계로 남아있음.
- mscz가 JSON 생성 이후 다시 수정되면(파일 mtime 비교) `--force`로 재생성.

### 3-2. 촬영 진행 중
- 곡당 20~30장, **폰/태블릿 × 종이/화면 촬영** 4가지 조합으로 진행 중.
- 화면 촬영도 실사용 시나리오로 확정(사용자 확인) — 모아레/화면 반사 아티팩트 포함해서 학습.

- 카메라 오버레이(오선 가이드)는 UI 레이어에서만 그려지고 `takePicture()` 원본 캡처엔 합성되지
  않으므로, 학습 데이터에 가이드 표시를 넣을 필요 없음(`lib/screens/guided_camera_screen.dart` 확인 완료).

### 3-3. 파인튜닝 시 유의사항 (계획)
- **곡 단위 홀드아웃 검증**: 같은 곡 사진끼리 이미지 단위로 무작위 분할하면 검증 정확도가
  부풀려짐 — 일부 곡(예: 100곡 중 10~15곡)은 통째로 학습에서 빼고 검증 전용으로 사용.
- **저학습률 + 합성 데이터 리플레이**: 과적합/망각 방지.
- **조기 종료**: 곡 단위 홀드아웃 검증 정확도가 정체/하락하는 시점 기준(에폭 수를 무작정
  늘리는 것보다 중요).
