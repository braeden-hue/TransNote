# 부스 컴패니언 페이지(스마트폰 QR) 계획

**상태**: 계획 수립 중(2026-08-10), 구현 전. docs/archive/PLAN_r18_grand_staff_scope.md와 별개 —
이쪽은 웹앱/전시 운영 기능, 학습 파이프라인과 무관.

## 목표

부스 키오스크(태블릿 + 전자피아노, 현재 메인 화면 그대로)와 별개로, 방문자가 스마트폰으로
QR을 스캔하면 **다른 화면**(같은 배포, 다른 URL)으로 연결되게 한다. 튜토리얼처럼 세로/작은
화면에 안 맞는 콘텐츠는 애초에 이 경로에 넣지 않는다(숨기는 게 아니라 아예 별도 페이지).

**점수 채점 로직은 새로 만들지 않는다** — 키오스크의 기존 연주하기 채점(전자피아노 MIDI +
`expPerform` 상태)을 그대로 재사용한다. 이번에 새로 만드는 건 그 결과를 Firestore로
실시간·기기간 공유되게 하는 것뿐이다.

**2026-08-10 수정: 로그인을 리더보드 흐름에서 완전히 뺌.** 애초 구상은 "로그인 후 연주 →
점수 명단"이었으나, 구글 OAuth 팝업(계정 선택+동의 화면+네트워크 왕복)이 닉네임 텍스트
입력보다 훨씬 느려서 대기줄이 있는 부스의 빠른 회전율 요구와 안 맞는다는 지적(사용자)에
따라 재설계함. 키오스크는 지금처럼 로그인 없이 닉네임만 입력 → 연주 → 점수 저장, 그대로
유지. 로그인 자체는 이번 기능에서 아예 제외(아래 항목들 참고). 기존 `firebase.js`의 구글
로그인(개인 악보 클라우드 저장)은 이 리더보드 기능과 무관하게 그대로 유지.

## 스마트폰 페이지 구성 (3개 구역)

1. **프로젝트 소개 (첫 화면 겸용)** — 메인 화면의 "프로젝트에 대해" 모달과 **같은 콘텐츠**를
   재사용. 현재 모달 내용(`webpage/index.html` `#about-modal`)은 명시적으로 "임시 초안"
   상태라, `designKit/3기 기획안.png`가 보여주는 온라인 전시 포맷(작품소개+팀 프로필/링크+
   서비스소개서·구동영상·깃허브 링크)에 맞춰 내용을 확장해야 함.
   **→ 팀원 이름/프로필/포트폴리오 링크/데모 영상 URL/깃허브 URL 등 실제 자료가 필요함
   (지어낼 수 없는 부분).**
2. **악보 촬영 → 인식 → 듣기** — 기존 체험하기 카메라 모듈(갤러리 선택 포함) 그대로 재사용.
   연주하기(MIDI 채점) 단계는 제외 — 폰에 실물 피아노가 없으므로 애초에 해당 없음.
3. **점수 확인** — 로그인 없이 전체 순위 바로 노출 + 닉네임 검색으로 "내 점수" 찾기.
   Firestore 기반, 실시간 갱신.

## 키오스크 ↔ 리더보드 연동 메커니즘

**이전 안(로그인 게이트)의 문제**: 구글 OAuth 팝업(계정 선택+동의 화면+네트워크 왕복)이
닉네임 텍스트 입력보다 훨씬 느려서, 대기줄이 있는 부스의 빠른 회전율과 안 맞음(사용자 지적,
2026-08-10). 로그인을 아예 빼는 쪽으로 재설계.

**확정안**: 로그인 없이 닉네임 문자열만으로 연동.
- 키오스크: 연주하기 진입 화면(`#exp-nickname-input` 텍스트 입력) **변경 없음** — 로그인
  절차 추가 안 함, 지금 속도 그대로 유지.
- 점수 저장: 로그인 없이 `{nickname, songKey, score, maxScore, createdAt}`을 Firestore에
  공개 쓰기(uid 없음).
- 스마트폰 "점수 확인" 탭: 로그인 없이 전체 순위(모든 방문자 점수)를 바로 보여줌. "내 점수"는
  uid 필터링이 아니라 **자기가 쳤던 닉네임을 검색창에 입력해 그 목록에서 찾는 방식**(즉시
  텍스트 필터, 인증 불필요)으로 대체.
- 기존 `firebase.js`의 구글 로그인(개인 악보 클라우드 저장, `scores` 컬렉션)은 이 리더보드
  기능과 완전히 무관하게 그대로 둠 — 엮지 않음.

**카카오 로그인**: 위 재설계로 이 기능엔 아예 해당 없음(로그인 자체를 안 씀). 필요 없어짐.

**닉네임 중복 처리 (2026-08-10 확정, 2026-08-10 스코프 재확정)**: 닉네임 유일성은
**곡(songKey) 안에서만** 검사 — 다른 곡에서는 같은 닉네임을 다시 써도 됨(전체 리더보드
공통 유일성 아님). uid가 없으니 "songKey+닉네임" 조합이 사실상의 식별자. 연주하기 진입
시 입력한 닉네임이 그 곡 리더보드에 이미 있으면 저장을 막고 "이미 사용 중인 닉네임이에요,
다른 닉네임을 입력해주세요" 안내 후 재입력받음(자동으로 숫자를 붙이는 등의 처리는 안 함).
닉네임 미입력 시 기본값 '익명'은 여러 명이 동시에 쓸 수 있어야 하므로 중복 체크에서
제외(구현 완료: `webpage/js/firebase.js`의 `isNicknameTakenInSong()`, `app.js`의
`exp-start-perform-btn` 클릭 핸들러).

**전화번호 입력 (기프티콘 지급용, 2026-08-10 확정)**: 전원에게 요구하지 않음. 연주하기
완료 화면에 "기프티콘 받고 싶으면 연락처 남기기"를 **선택 사항**으로 노출 — 원하는 사람만
입력, 나머지는 닉네임만으로 진행.

주의: `leaderboard` 컬렉션은 읽기가 완전 공개라, 전화번호를 그 문서 안 필드로 같이 저장하면
Firestore 보안 규칙은 문서 단위라 필드만 숨기는 게 안 됨 — 순위를 보는 아무나 전화번호까지
같이 읽을 수 있게 됨(개인정보 유출). 그래서 전화번호는 **별도 컬렉션**으로 분리:
`leaderboard_contacts/{entryId}: { nickname, phone, createdAt }` — 쓰기는 공개 허용, 읽기는
**차단**(`allow read: if false`, 즉 스태프가 Firebase 콘솔에서만 확인 가능한 쓰기 전용
저장소). `entryId`를 `leaderboard`의 해당 항목과 동일하게 맞춰서 나중에 매칭 가능하게 함.

## Firestore 스키마 변경

기존 `firebase.js`의 `scores` 컬렉션(개인 클라우드 저장용, 구글 로그인 필요)은 그대로 유지,
이번 기능과 무관. 새 컬렉션 추가:

```
leaderboard/{entryId}: {
  nickname, songKey, score, maxScore, createdAt
}
```

- 쓰기: **비로그인 공개 쓰기 허용** — `leaderboard` 컬렉션 하나만 예외적으로 인증 없이
  써지게 보안 규칙을 설정(다른 컬렉션은 기존대로 로그인 필요). 누군가 프로젝트 ID를 알아내면
  이론상 이 컬렉션에 스팸을 넣을 수 있는 트레이드오프가 있지만, 하루짜리 전시 부스 규모에서는
  감수할 만하다고 판단(2026-08-10 재확인).
- 읽기: 공개(로그인 무관).

**구현 완료(2026-08-10)**: `webpage/js/firebase.js`에 `isNicknameTakenInSong()`/
`saveLeaderboardEntryCloud()`/`loadLeaderboardCloud()` 추가(모두 `_db` 존재만 확인, 로그인
불필요). `app.js`의 `saveLeaderboardEntry()`/`loadLeaderboard()`(기존 `localStorage`)를
제거하고 `renderLeaderboard()`를 async로 바꿔 `loadLeaderboardCloud()` 호출로 교체.
`finishExpPerform()`은 `saveLeaderboardEntryCloud()` 호출로 교체(실패해도 조용히 무시 —
저장 실패가 이미 끝난 연주 체험을 막으면 안 됨). `exp-start-perform-btn` 클릭 핸들러가
연주 시작 전에 `isNicknameTakenInSong(songKey, nickname)`으로 곡 안 중복을 검사하고,
겹치면 `#exp-nickname-error`(신규 HTML/CSS)에 안내 문구를 띄우고 진행을 막음(`익명` 기본값은
검사 제외). 확인 실패(네트워크 등)는 막지 않고 통과 — 체험이 우선.

**주의(미해결, 콘솔 수동 작업 필요)**:
1. **Firestore 보안 규칙을 아직 콘솔에 안 넣음** — 지금 상태로는 `leaderboard` 컬렉션 쓰기가
   기본 규칙(대개 전체 차단 또는 테스트 모드의 시간제한 전체 허용)에 걸려 있을 수 있음. 아래
   규칙 텍스트를 Firebase 콘솔 → Firestore Database → 규칙 탭에 붙여넣어야 실제로 동작함:
   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /leaderboard/{entryId} {
         allow read: if true;
         allow create: if true;
         allow update, delete: if false;
       }
       match /leaderboard_contacts/{entryId} {
         allow read: if false;
         allow create: if true;
         allow update, delete: if false;
       }
       match /scores/{scoreId} {
         allow read, write: if request.auth != null && request.auth.uid == resource.data.userId
                             || (request.auth != null && request.method == 'create');
       }
     }
   }
   ```
   (`scores` 규칙은 기존 동작 그대로 유지하려는 최소 근사치 — 실제 콘솔에 이미 다른 규칙이
   있다면 `leaderboard`/`leaderboard_contacts` 블록만 추가하고 `scores` 블록은 기존 것을
   건드리지 않는 게 더 안전함.)
2. **`where(songKey==)+orderBy(score desc)` 복합 쿼리는 Firestore 복합 색인이 필요** —
   `loadLeaderboardCloud()`를 처음 실제로 호출하면(배포 후 브라우저 콘솔에러로) Firestore가
   "색인 생성 필요" 에러와 함께 자동 생성 링크를 줌. 그 링크를 한 번 클릭해서 색인을 만들어야
   실제로 쿼리가 동작함 — 코드로 못 하는 부분, 배포 후 실제 클릭 테스트 시 발견될 것.
3. 위 두 가지 다 브라우저/Firebase 콘솔 접근이 필요해서 여기서 직접 처리 불가 — 배포 후
   사용자가 직접 확인해야 함.

- 스마트폰 "점수 확인" 탭의 닉네임 검색은 클라이언트 사이드에서 `nickname` 필드 부분 일치
  필터(Firestore 쿼리 or 전체 리스트 로드 후 JS 필터, 부스 규모면 후자로 충분) — 아직 미구현.

## 온라인 전시 제출 요건 대응 (2026-08-10, 전시 측 조건 공지 반영)

전시 측 공지: URL 제출(웹호스팅), 뷰페이지 내 iframe 임베드, 트래픽/서버는 팀 책임, **반응형
구축 필수**. 우리 아키텍처(Vercel 배포)는 URL/호스팅 조건은 이미 충족. 아래 두 개가 실제
작업 필요한 항목.

### iframe 허용 자체 — 확인 완료, 이미 충족

`vercel.json`/`server.py`/`api/*.py` 어디에도 `X-Frame-Options`/`Content-Security-Policy:
frame-ancestors`/`Permissions-Policy` 헤더 설정이 없음(2026-08-10 코드 확인) → 기본값이라
iframe 삽입 자체는 이미 막혀있지 않음. 제출 전 실제 테스트 iframe으로 한 번 더 확인 권장.

### 카메라/MIDI 권한 — 우리 코드로 못 고치는 부분 + 방어책

**문제**: iframe 안에서 카메라(체험하기)/MIDI(연주하기) 접근은 부모 페이지의
`<iframe allow="camera; midi *">` 속성이 없으면 브라우저가 자동 차단함 — 전시 사이트의
임베드 코드에 달려있어 우리 쪽에서 코드로 해결 불가.
- **전시 측에 요청 필요**: `allow="camera; microphone; midi *"` 속성을 iframe 태그에
  넣어달라고 명시적으로 전달(사용자가 직접 전시 운영 측에 확인).
- **방어책(구현 가능)**: `window.self !== window.top`으로 iframe 내부 실행 감지 →
  getUserMedia/MIDI 요청이 거부되면 "카메라/피아노 권한이 제한된 환경입니다 — 새 탭에서
  크게 열기" 버튼 노출(`window.open(location.href, '_blank')`로 iframe 밖 전체 페이지를
  새로 열어 우회). 전시 측 설정 여부와 무관하게 항상 동작하는 안전망.

### 반응형 — 코드 작업 필요

지금은 두 상황만 대응됨: 키오스크(고정 landscape 비율, `zoom` 기반 auto-fit — 비표준)와
`/m` 폰 컴패니언(세로 스크롤). 이번 요건은 **크기를 모르는 세 번째 상황** — 전시 사이트가
자기 뷰페이지 안 임의 크기의 iframe에 우리를 박아넣음. 랜딩(사진 배경+액자 핫스팟)은
landscape 비율 가정 디자인이라, iframe이 세로로 길거나 정사각형이면 그림이 잘리거나 핫스팟
위치가 어긋날 위험 있음.

**해결 방향**:
1. 랜딩 씬(배경+핫스팟)을 원본 비율로 고정한 wrapper(`aspect-ratio` + `max-width`/
   `max-height` 중앙 정렬)로 감싸서, 어떤 컨테이너 크기에서도 전체가 레터박스로 축소
   표시되게 함 — 핫스팟이 `%` 좌표라 wrapper 안에서 비율만 유지되면 정렬 안 깨짐.
2. 뷰포트 폭 기준 미디어 쿼리 breakpoint 추가 — 좁은 폭(세로형 iframe/폰)에서는 `/m`과
   같은 스택형 레이아웃으로 전환.
3. 대표 크기 3종(가로로 넓게/세로로 길게/정사각형)에서 실제 렌더 테스트, 카메라/피아노 버튼이
   좁은 프레임에서도 눌리는지 확인.

`/m` 작업과 방향이 겹쳐서, 반응형 CSS를 제대로 잡아두면 이 요건도 같이 해결될 가능성 높음.
