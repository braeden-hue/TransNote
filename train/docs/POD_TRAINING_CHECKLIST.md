# Pod 데이터 생성/학습 시작 전 체크리스트

새 RunPod을 켜고 데이터 생성 → 학습을 시작하기 전에, 아래를 **순서대로** 확인한다.
전부 2026-07-31 세션에서 실제로 학습이 4시간 동안 반복 실패한 원인들에서 도출됨.

## 1. 컨테이너 메모리 한도 확인 (free -h 믿지 말 것)

```bash
cat /sys/fs/cgroup/memory.max   # 이게 진짜 한도. free -h는 호스트 전체를 보여줘서 훨씬 큰 값이 나옴
```

- 실측 사례: `free -h`는 440GB로 보였지만 실제 cgroup 한도는 약 50GB뿐이었음.
- `dataset.py`의 `ThreadPoolExecutor(max_workers=N)`과 `train.py --workers N`(DataLoader
  `num_workers`, 별도 프로세스)은 서로 다른 개념이다. 둘 다 이 한도 안에서 결정할 것.
  워커 수를 늘려서 문제가 생기면 먼저 이 값부터 다시 확인.

## 2. MuseScore 헤드리스 렌더는 반드시 xvfb-run으로 감쌀 것

```bash
xvfb-run -a python3 generate_scores.py ...   # 이렇게 바깥에서 감싸야 함
```

- `render_png()`/`render_batch_png()` 내부 `subprocess.run([musescore, ...])`는 X 디스플레이가
  없으면 **에러 없이 조용히 즉시 실패**한다(수 초 안에 "실패"로 끝남 — 렌더링을 시도조차 안 함).
  이 실패는 두 함수 모두 정상적인 "빈 페이지/2시스템 감지 후 스킵" 경로와 똑같이 보여서
  알아채기 매우 어렵다. **몇 장만 먼저 xvfb-run 없이 실행해보고 즉시(수 초 내) 끝나면
  의심할 것.**

## 3. 렌더링 직후 실제 픽셀 크기를 확인할 것 (스크립트가 버그 없다고 가정하지 말 것)

```bash
python3 -c "import cv2; im=cv2.imread('<하나만 골라서>.png'); print(im.shape)"
```

- 2026-07-31 실측 버그: `render_batch_png()`(배치 -j 모드, 대량 생성 때 실제로 쓰이는 경로)가
  `-r 150` 해상도 플래그 없이 호출되고 있어서 MuseScore 기본값(1200dpi)으로 렌더됨 —
  가로세로 각 8배(픽셀수 64배) 큰 이미지가 나왔다. `render_png()`(단일 렌더, 데모/테스트용)는
  `-r 150`을 제대로 넘기고 있어서 **테스트할 땐 정상, 실제 대량 생성만 깨져있었음** — 두 경로가
  동일한 인자를 쓰는지 항상 직접 대조할 것.
- 이 버그는 학습 시작 직후 `OMRDataset.__init__`의 전처리 단계에서 컨테이너 메모리 한도를
  즉시 초과시켜 exit 137(OOM-kill)을 유발했다. 워커 개수를 아무리 조정해도 해결 안 됨 —
  범인은 이미지 자체였다.
- **중요**: 이미 잘못 렌더된 이미지를 사후에 다운스케일(리사이즈)해서 고치려 하지 말 것.
  고해상도에서 오선/바라인 같은 얇은 요소가 "최소 두께 1px" 등으로 고정 렌더되면, 다운샘플
  시 8x8 박스 평균으로 거의 흰색에 가깝게 뭉개져서 `detect_staffs()`가 대량(실측 70%)으로
  실패한다. 저장된 `.musicxml`에서 **올바른 DPI로 재렌더링**해야 한다(콘텐츠/토큰 라벨은
  이미 확정돼 있으니 재생성 불필요, MuseScore 재구동만 하면 됨 — 훨씬 빠름).

## 4. 원격 pod SSH 세션에서 백그라운드 실행 시 nohup+& 금지

- 로컬 작업에 대한 기존 규칙([[feedback-no-disown-background]])이 **원격 pod SSH 세션에도
  동일하게 적용됨**을 2026-07-31 확인: `ssh ... "cmd & echo LAUNCHED"` 패턴으로 띄운 프로세스가
  SSH 세션이 끝나자마자(또는 그 직후) 죽어서, "따로 빠르게 polling하려고" 분리시킨 프로세스가
  실제로는 몇 초도 못 버티고 사라짐.
- 항상 Bash 도구의 `run_in_background: true`로 SSH 명령 자체를 하나의 추적 가능한 작업으로
  띄우고, 상태 확인은 **별도의 새 SSH 연결**(빠르게 붙었다 끊는)로 로그 파일을 tail하는 식으로
  분리할 것 — 원본 SSH 세션은 절대 끊지 않는다.

## 5. 데이터 생성 병렬화 설정 (2026-08-02 실측, 지금까지 중 가장 빠름)

새 pod를 켰을 때 아래 순서로 확인하고 그대로 적용하면 이번 세션과 동일한 속도가 나온다.

```bash
cat /sys/fs/cgroup/cpu.max      # 예: "1360000 100000" -> 13.6코어가 진짜 한도
nproc                            # 예: 128 -- 이 숫자를 그대로 쓰면 안 됨(과다 병렬화)
```

- **N_SHARDS는 nproc이 아니라 cpu.max 코어 수 기준으로 잡을 것.** 이번 세션 pod(cpu.max
  13.6코어)에서 `N_SHARDS=6`(`generate_scores.py`를 xvfb-run으로 감싼 프로세스 6개 병렬)이
  가장 안정적이면서 빨랐다 -- 실측: 2000장(단일오선 300+대보표 1700, 마디 1~4개)을
  **109초**에 생성(약 18장/초). 대략 "cpu.max 코어 수의 절반 정도"가 안전선(메인 bash
  오케스트레이션 + xvfb 자체 오버헤드 감안).
- N_SHARDS를 cpu.max보다 훨씬 크게 잡으면(예전에 32까지 써봤던 사례) xvfb-run 동시 실행
  경쟁으로 일부 샤드가 렌더링 실패하거나(item 2 참고), 컨테이너 메모리 한도(item 1)를
  넘겨 OOM-kill 위험이 커진다 -- 6이 "적당히 병렬화하면서도 안전한" 균형점으로 확인됨.
- 표준 실행 패턴(그대로 복사해서 씀):
  ```bash
  for i in $(seq 0 5); do   # N_SHARDS=6
    xvfb-run -a python3 generate_scores.py \
      --count "$THIS_COUNT" --output "$POOL_DIR" --musescore "$MUSESCORE" \
      --start-idx "$SHARD_START" --seed "$SHARD_SEED" "${BASE_ARGS[@]}" \
      > "/workspace/gen_shard_${i}.log" 2>&1 &
  done
  wait
  ```
- 이 값(N_SHARDS=6)은 GPU 학습과 **동시에 CPU만으로** 돌려도 문제없었다(2026-08-02, Round
  학습 중 다음 라운드 데이터를 미리 생성해서 시간 절약 -- GPU/CPU 자원이 분리돼 있어 안전).

### 참고 정정: 원격 pod 백그라운드 실행에 `nohup ... &`는 문제없음

이 문서 4번 항목("nohup+& 금지")은 **`nohup 없이 그냥 &`만 쓴 경우**에 대한 경고였는데
문구가 오해의 소지가 있었다. 2026-08-02 세션에서 `ssh ... "nohup bash script.sh >
/dev/null 2>&1 & echo PID=$!"` 패턴(Bash 도구의 `run_in_background:true`로 SSH 명령
자체를 감쌈)을 수십 회 반복 사용했고, 몇 시간 뒤 별도 SSH 재접속으로 확인해도 프로세스가
전부 살아있었다(학습이 몇 시간씩 걸려도 문제없이 지속). **`nohup`을 반드시 붙이면 SSH
세션이 끊겨도 안전하다** -- 4번 항목이 실제로 경고하는 건 nohup 없이 맨 `&`만 쓰는
경우다.

## 6. 학습이 "에폭을 돌기 시작"해도 데이터 품질을 검증할 것

- `[OMRDataset R3] N samples (M skipped)` 로그의 skipped 비율을 반드시 확인. 학습이 죽지 않고
  에폭이 진행돼도(2026-07-31: Acc=95.9%까지 찍었음) 그 자체가 데이터가 정상이라는 증거는
  아니다 — 73% 스킵된 편향 데이터로도 GPU 학습 루프는 멀쩡히 돈다.
- 소량(30~50장) 샘플에 대해 `_load_one()` 로직을 직접 재현해 스킵 사유별 카운트를 찍어보는
  진단 스크립트를 새 대량 데이터마다 한 번씩 돌려볼 것.
